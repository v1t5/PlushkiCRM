# Architecture

Architecture for **PlushkiCRM** — a management system for bakery production and a light café POS,
organised around the bounded contexts of bakery production and in-person cafe sales.

This document captures intent. Concrete technical decisions are flagged as **(decision)**; open ones
are flagged as **(open)**.

## Goals

**Domain.** Centralised order intake (Telegram + cafe POS + future web), inventory and stock movement,
daily production planning for bakers, light in-person cafe sales, basic customer CRM.

**Non-functional.**

- Asynchronous, message-driven communication between services. No synchronous dependency chain across
  more than one hop.
- Structured logging and distributed tracing from day one — every request and event is observable
  end-to-end.
- Single-tenant build, but data carries `tenant_id` so multi-tenancy is a configuration switch later,
  not a rewrite.
- Light POS — no fiscal printer or card acquiring in v1.

## Shape

```
                       ┌─────────────┐
                       │   Caddy     │  TLS, routing, auth introspection
                       │  (gateway)  │
                       └──────┬──────┘
                              │ HTTP/JSON
            ┌─────────────────┼──────────────────┐
            ▼                 ▼                  ▼
      ┌─────────┐       ┌──────────┐      ┌──────────┐
      │ identity│       │  orders  │      │ catalog  │  ... etc
      └────┬────┘       └─────┬────┘      └────┬─────┘
           │ events           │                │
           └──────────┬───────┴────────────────┘
                      ▼
             ┌──────────────────┐
             │    RabbitMQ      │
             │ (topic exchanges)│
             └────────┬─────────┘
                      │
       ┌────────┬─────┴─────┬─────────┬──────────┐
       ▼        ▼           ▼         ▼          ▼
   inventory production notifications crm    reporting
```

External adapters (Telegram bot, web admin, POS frontend) call the gateway. They never call services
directly.

## Foundational decisions

Locked-in choices that apply across every service. Captured here so they're not re-litigated per
service.

| Topic | Decision |
|---|---|
| **Repo layout** | Monorepo. Every service at `services/<svc>/` with its own `composer.json` and `src/`. No shared PHP package — each service carries its own copy of cross-cutting utilities under `src/Platform/`. |
| **Identifiers** | UUID v7 for every aggregate root. Generated by the service (no DB round-trip to assign). Sortable by creation time, plays well with btree indexes and `outbox` ordering. |
| **Money** | `int` kopecks across domain, API, and DB. Never `float`. Never `decimal` either — conversion to rubles is a presenter-layer concern (frontends, Telegram messages, receipts). |
| **Database isolation** | **One Postgres container per service.** Own image, own volume, own backup schedule, own credentials. Cross-service SQL is physically impossible — state propagation happens through events. A service's database going down does not affect other services. |
| **Code sharing between services** | **None at compile time.** No shared Composer package. Each service is its own `composer.json` with its own copy of cross-cutting utilities (logging, OTel, AMQP client, healthcheck, config). Improvements to platform code are propagated by hand, not by dependency bump. This is what makes services independently deployable in the strict sense. |
| **Customer identity model** | `Customer` has a stable internal `id` (UUID v7). External identities — TG user id, phone, email — are rows in `customer_identities (customer_id, type, value, verified_at)`, not columns on `customer`. A single human can be linked from TG, phone login, and email login without duplication. |
| **Order state machine** | `draft → placed → confirmed → in_production → ready → completed`. `cancelled` reachable from any state up to and including `ready`. No transitions out of `completed` or `cancelled` in v1. Returns and corrections are out of scope until Phase 4+. |
| **Tenant scope** | `tenant_id` on every aggregate, hardcoded `'default'` in v1. See [Multi-tenancy](#multi-tenancy). |
| **Time** | All timestamps stored as `timestamptz` in UTC. `Europe/Moscow` is a presentation concern. |
| **Soft-delete policy** | Master data (`products`, `customers`, `categories`, `recipes`, `warehouses`) carries `archived_at timestamptz NULL`; default query helpers filter it out. Transactional / append-only tables (`orders`, `stock_movements`, `outbox_events`, reporting projections) are never updated or deleted retroactively — corrections happen via new rows or compensating events. |
| **API errors** | RFC 7807 `application/problem+json`. Stable machine-readable `type` URIs (e.g. `https://errors.plushki/orders/state-conflict`). Frontends localise by `type`; response bodies never carry human-readable strings the client is expected to display verbatim. |

## Service catalog

Every service:

- Owns its own data. No foreign keys cross service boundaries — only logical references.
- Exposes HTTP/JSON for synchronous calls.
- Publishes domain events to RabbitMQ for asynchronous propagation.
- Subscribes only to events it needs.

| Service | Owns | Emits | Listens to |
|---|---|---|---|
| **identity** | users, roles, sessions, JWT keys | `identity.v1.user_created` | — |
| **catalog** | products, recipes (BOM), categories, units | `catalog.v1.product_updated`, `catalog.v1.recipe_updated` | — |
| **inventory** | warehouses, stock levels, stock movements | `inventory.v1.stock_changed`, `inventory.v1.low_stock` | `production.v1.task_completed`, `orders.v1.fulfilled` |
| **orders** | orders, line items, status transitions | `orders.v1.created`, `orders.v1.confirmed`, `orders.v1.cancelled`, `orders.v1.fulfilled` | — |
| **production** | daily plan, baker tasks | `production.v1.plan_published`, `production.v1.task_started`, `production.v1.task_completed` | `orders.v1.confirmed`, `inventory.v1.stock_changed` |
| **crm** | customers, loyalty | `crm.v1.customer_registered`, `crm.v1.loyalty_updated` | `orders.v1.fulfilled` |
| **notifications** | outbound message log, channel adapters | — | `orders.v1.*`, `production.v1.plan_published`, `inventory.v1.low_stock` |
| **reporting** | denormalised read models | — | all `*.v1.*` |

Edge / channel adapters:

- **gateway** — Caddy. Auto-TLS, routing, JWT introspection (calls identity).
- **tg-bot** — Telegram bot. Calls `orders`, `crm`, `notifications` via the gateway. Holds no business
  logic of its own.
- **pos-web** — minimal cafe POS frontend, Vue 3 SPA. Calls `orders` and `catalog` via the gateway.
- **admin-web** — operations UI for owner/staff, Vue 3 SPA.

## Multi-tenancy

- Every aggregate root has `tenant_id NOT NULL`.
- All queries filter by `tenant_id`.
- v1 ships with a single hardcoded tenant (`'default'`).
- Activation later requires:
  - tenant CRUD in identity,
  - JWT carrying a `tenant_id` claim,
  - gateway middleware passing it to services as a header,
  - row-level security or query-layer enforcement to keep tenants from leaking.

The cost of carrying `tenant_id` from day one is one extra column per table and one extra `WHERE`
clause. The cost of retrofitting it is a multi-week migration of every aggregate.

## Inter-service communication

**Synchronous (HTTP/JSON via gateway).**

- Read paths that need fresh data (POS reads catalog).
- Commands that need an immediate response (place order).

**Asynchronous (RabbitMQ events).**

- Cross-context state propagation (orders fulfilled → inventory deducts; orders confirmed → production
  schedules).
- Side effects (notifications, reporting projections).

**Rules.**

- Services do not read each other's databases.
- A service may call another service's HTTP API, but only via the gateway, so auth/observability stay
  uniform.
- Domain events are facts, named in past tense. They are not commands.
- A service is allowed to be unavailable. Callers degrade gracefully (cached data, queued retry).

## Authentication and authorization

Two layers, both terminate at the gateway. Services downstream trust the gateway's translation.

### End-user auth (humans)

- User logs in at `identity` with username + password.
- Identity issues a short-lived **access JWT** (15 min) and a **refresh token** (30 days, rotating,
  stored hashed).
- Access JWT claims: `sub` (user id), `tenant_id`, `roles[]`, `iat`, `exp`. Signed RS256.
- Identity publishes its public keys at `/.well-known/jwks.json`. Gateway validates JWTs locally with
  cached JWKS — no introspection round-trip on the hot path.
- Refresh flow: client posts refresh token to `identity/auth/refresh`, gets a new pair. Old refresh
  token is marked used.

Used by: `pos-web`, `admin-web`, future mobile apps, future customer-facing web.

### Service / bot auth

- Each non-human caller (`tg-bot`, internal cron, future admin tools, server-to-server calls) is
  provisioned a long-lived **service token** by identity.
- Token = opaque random 32-byte string, base32-encoded. Stored hashed (argon2id) in identity. Shown
  once at creation; not recoverable.
- Sent as `Authorization: Bearer <token>` to the gateway.
- Gateway introspects via `identity/auth/introspect`. Result cached in Redis for 60 s. Introspection
  returns `{actor_type: "bot"|"service", actor_id, tenant_id, scopes[]}` or 401.
- Tokens can be rotated/revoked from identity admin. Compromised tokens stop working within cache TTL.

Used by: `tg-bot` (one token, scope = `orders:write`, `crm:read`, `notifications:send`), internal jobs.

### Gateway → service envelope

After validating either credential, the gateway strips it and replaces it with a stable set of
internal headers passed to the upstream service:

```
X-Tenant-Id:    default
X-Actor-Type:   user | bot | service
X-Actor-Id:     <uuid>
X-Actor-Roles:  cashier,baker         (only for users)
X-Actor-Scopes: orders:write,crm:read (only for bots/services)
X-Trace-Id:     <w3c traceparent trace-id>
```

Services trust these headers because nothing reaches them except via the gateway (services are on a
private compose network, no published ports).

For local development, services accept a static `dev-token` shortcut when `APP_ENV=dev`, which lets you
`curl` them directly without going through the gateway.

## Messaging

**Routing-key naming.** `<context>.<version>.<event>[.<tenant_id>]` — e.g. `orders.v1.created.default`.
Tenant is the trailing segment so queue bindings can wildcard-match it (`orders.v1.fulfilled.*`) when
multi-tenancy activates.

**Exchange layout (RabbitMQ topic exchanges).**

- One durable topic exchange per context: `ORDERS`, `INVENTORY`, `PRODUCTION`, `CRM`, `IDENTITY`,
  `CATALOG`.
- Publishers send to their own exchange with `routing_key = <context>.v1.<event>.<tenant>`.
- Consumers own durable, named queues (e.g. `reporting-orders-fulfilled`). Each queue binds with a
  topic pattern like `orders.v1.fulfilled.#`.
- Messages are published with `delivery_mode = persistent`. Ack semantics: manual ack after the
  projection/handler commits; transient errors `nack(requeue=true)`; poison messages
  `nack(requeue=false)`.

**Event envelope (JSON).**

```json
{
  "event_id": "01HW...",
  "occurred_at": "2026-04-29T10:15:00Z",
  "tenant_id": "default",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "actor": { "type": "user|system|bot", "id": "..." },
  "schema": "orders.v1.created",
  "data": { "...": "domain payload" }
}
```

**Outbox pattern.** Services publish to RabbitMQ via a transactional outbox table (`outbox_events`)
plus a background relay. This guarantees that a state change and its event are atomic — no event is
lost if the publisher crashes after `COMMIT` but before the broker publish.

**Idempotency.** Consumers dedupe on `event_id` at the DB layer (unique indexes or `applied_events`).
RabbitMQ delivers at-least-once.

**Schema evolution.** Event schemas are plain JSON validated against `schemas/events/*.json` **(open)**.
Breaking changes bump the version (`orders.v1` → `orders.v2`) and run side by side during migration.

## Observability

**Logging.**

- All services emit JSON to stdout via Monolog.
- Promtail ships logs to **Loki**.
- Standard fields on every line:
  ```
  ts, level, svc, env, tenant_id, trace_id, span_id, msg
  ```
- Plus arbitrary structured attributes. No string interpolation in messages — values go in attrs.

**Tracing.**

- OpenTelemetry SDK in every service.
- Trace context propagated via the `traceparent` header on HTTP and via the envelope `trace_id` on
  AMQP messages.
- Spans exported (OTLP) to **Tempo**.

**Metrics.**

- Prometheus scrapes `/metrics` on every service.
- RED metrics (rate, errors, duration) per HTTP route and per AMQP routing key.
- Business metrics: orders/min, production task queue depth, low-stock count, notification send rate.

**Dashboards.** **Grafana** is the single pane: logs (Loki), traces (Tempo), metrics (Prometheus).

## Deployment

- **Dev:** `docker compose up`, composed of per-service compose snippets layered over a shared infra
  stack. Each service builds from its own folder.
- **Prod (single-host MVP):** the same compose set with prebuilt images, fronted by Caddy with
  auto-TLS.
- **Scale-out:** services are 12-factor and stateless. Moving to a Kubernetes cluster is a deployment
  change, not a code change.

### Infrastructure topology

| Component | Topology | Notes |
|---|---|---|
| **Postgres** | One container per service (`identity-db`, `catalog-db`, `orders-db`, ...) | Own volume, own backup. Each service connects only to its own DB. |
| **RabbitMQ** | Single shared broker | Messaging substrate; shared by definition. Management UI on `:15672`. |
| **Redis** | Single shared instance | Caches and rate-limit counters. Per-service prefixes (`identity:`, `orders:`). Promote to per-service if isolation demands. |
| **Caddy gateway** | Single instance | API gateway pattern — one public entry. |
| **Loki / Tempo / Prometheus / Grafana** | Single shared stack | Centralised observability is the point. |
| **Identity service** | Single instance | Auth provider for everyone, called via the gateway. |

## Repository layout

All services live under [services/](../services/) in this repository, but each is fully independent:

```
services/
  identity/             # own composer.json, own Dockerfile, own src/Platform
  catalog/
  orders/
  inventory/
  production/
  crm/
  notifications/
  reporting/
  logger/               # event sentinel (stateless)
  tg-bot/               # Telegram bot
  pos-web/              # Vue 3 + Vite, own package.json
  admin-web/            # Vue 3 + Vite, own package.json
  _template/            # scaffolding skeleton copied when starting a new service
```

There is **no shared PHP package** in this repo. Monorepo here means "sibling working copies live next
to each other for convenience" — not "shared compile-time code". Moving any service to its own GitHub
repo is a copy operation with no code changes.

## Service layout

Every service is an independent Symfony app with the same internal shape — ports & adapters — so a
reader switching between services finds the same structure each time.

```
services/<svc>/
  composer.json              # own dependencies. PSR-4 root: Plushki\<Svc>\ → src/.
  Dockerfile                 # builds this service alone.
  bin/console                # Symfony console entrypoint (migrate, relay, consumers).
  public/index.php           # HTTP front controller (served by FrankenPHP).
  src/
    Kernel.php               # wire-up: config, logger, OTel, AMQP, DB, routing.
    Domain/                  # pure PHP types and invariants. No Symfony, no I/O.
    App/                     # usecases. Orchestrate domain + ports. Thin.
    Ports/                   # interfaces app expects from adapters.
    Adapters/
      Http/                  # controllers, DTOs, problem+json error mapping.
      Db/                    # DBAL repositories with hand-written SQL.
      Events/                # AMQP publisher + outbox relay + consumer wiring.
    Platform/                # this service's own copy of cross-cutting utilities:
                             # Monolog setup, OTel init, AMQP client wrapper, config
                             # loader, migrator, healthcheck, problem+json helpers.
                             # NOT shared with other services.
  migrations/                # plain .sql files (goose-annotated up/down).
  config/                    # optional yaml overlay (config.example.yaml).
```

Layer rules, enforced by review:

- `Domain` is pure PHP only. No HTTP, no SQL, no AMQP, no logger, no Symfony.
- `App` depends on `Domain` and `Ports`. A usecase validates input, loads an aggregate via a port,
  mutates it via domain methods, persists via a port, emits an event via a port. No raw SQL, no HTTP
  types.
- `Ports` are interfaces only — no implementation.
- `Adapters` depend on `Ports`, `Domain`, `Platform`, and tech libraries.
- `Platform` depends on PHP + tech libraries only. Does not depend on `Domain` or `App`.
- `Kernel` wires the runtime — it depends on `Adapters`, `App`, `Platform`.
- **No service ever imports another service.** The only inter-service couplings are HTTP (through the
  gateway) and AMQP events. There is no namespace dependency between services.

### Why no shared module

Compile-time sharing breaks independent deployability — bumping a shared dependency forces every
service to rebuild and redeploy. Strict microservices treat each service as independently versioned and
independently deployed. The cost is a small amount of duplication: ~100–200 lines of platform code per
service. The benefit is that any service can move to its own repo, switch language, or be deleted
without touching its neighbours.

When scaffolding a new service, copy `src/Platform/` from a recent service (or from `_template/`) as a
starting template. Future improvements are propagated by hand. This mirrors how separate teams in a
real microservice org maintain their own copies of cross-cutting code.

## Tooling baseline

Repo-wide standards. No service opts out.

- **Static analysis:** PHPStan at a high level across `src/`.
- **Style:** a shared PHP-CS-Fixer / coding-standard ruleset.
- **Tests:** unit tests for `Domain`/`App` run without infrastructure (in-memory port fakes).
  Integration tests run against real Postgres/RabbitMQ/Redis in Docker — no mocks of database or queue.
- **Migrations:** every migration has a tested `down` step.

## What's not in v1

Deliberately deferred to keep v1 shippable:

- Fiscal printer / online cash register.
- Card acquiring.
- Delivery routing / courier app.
- Loyalty beyond visit count + total spent.
- Multi-tenant runtime (column is there; activation isn't).
- Kubernetes.
